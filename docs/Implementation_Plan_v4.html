1. Goals

  • Self-service sign-up: a firm signs up, chooses its domain and immediately gets a CRM shaped for that profession (objects, fields, stages, terminology, dashboards, roles).
  • Complete isolation between firms (tenants): no query, cache, file, e-mail link or background job can cross tenants.
  • Fast: pages feel instant after the first load; API answers in tens of milliseconds even with the database in another region.
  • Keep everything built so far (v3 engine, apps, security, portal, packs). Existing data becomes the first tenant.

3. Multi-tenant architecture

Decision: one PostgreSQL schema per tenant (firm), plus a small shared platform schema.

ConcernDesign
Why schema-per-tenantStrong isolation with no tenant column to forget in thousands of queries; the existing engine, seeds and migrations work unchanged inside each schema; per-tenant backup/restore and deletion are simple. Suits a professional-firm SaaS (hundreds to low thousands of tenants).
Platform schematenants (id, slug, firm name, domain, schema name, status, region, created/verified dates), user_directory (e-mail → tenant + user, for sign-in), signup_requests (verification tokens), provisioned_schemas (warm pool), platform audit log.
Routing a requestThe session cookie carries the tenant id with the token (<tenant>.<token>). Each transaction starts with SET LOCAL search_path = <tenant schema>, which is safe with Neon's pooled (PgBouncer transaction-mode) connections.
CachesEvery in-memory cache (registry, permissions, sharing context, settings) is keyed by tenant and revision.
Links in e-mailsInvitation, reset, verification, unsubscribe and tracking links carry the tenant, so public endpoints resolve the right schema.
Background jobsEvery job carries its tenant; scheduled jobs (reminders, escalations, retention, scheduled reports) iterate active tenants.
FilesStorage keys prefixed by tenant; downloads check the tenant.
MigrationsPlatform migrations once; tenant migrations applied to every tenant schema (CLI migrate-tenants, also run on deploy).
Existing dataThe current public schema becomes the first tenant, so no data is moved.

4. Sign-up and sign-in

  1. Sign-up page (public): choose a domain from four cards (with a one-line description of what each includes), then firm name, your name, work e-mail, password, ABN (optional), and acceptance of terms and privacy policy.
  2. Verify e-mail: a single-use link (24 h). Unverified sign-ups are removed after 7 days.
  3. Workspace creation: takes a pre-built schema from a warm pool (instant), otherwise builds one in the background with a progress screen (target < 10 s). Installs the domain pack, applies domain-first navigation and terminology, creates the firm's administrator (System Administrator profile, MFA enrolment at first sign-in in production).
  4. First-run guide on the home page: invite colleagues, import clients (CSV), set company/billing details, connect e-mail sending.
  5. Sign-in: e-mail + password. If the e-mail belongs to several workspaces, a workspace picker appears. Portal clients sign in the same way and land in their firm's portal.
  6. Abuse controls: rate limits per IP and e-mail, reserved/blocked slugs, verification before use, CAPTCHA hook.

5. Domain-specific CRMs

  • Domain-first navigation: the domain's app is the main app (Home, Clients, Matters/Engagements/Loans…, Calendar, Reports). Generic Sales, Service, Marketing and Billing apps are hidden (not deleted) and can be switched on in Setup → App Manager.
  • Terminology: standard objects are renamed for the profession (e.g. Contact → Client, Account → Organisation/Entity, Opportunity → Enquiry), and every label, list view and report follows.
  • Defaults: stage paths, list views, home cards, dashboards, report library, document checklists, profiles and roles suited to the profession.
  • Branding: the workspace carries the firm's name; colours default per domain.

7. Security and isolation

  • Tenant resolved from the signed session cookie only (never from user input); the tenant id must exist and be active.
  • The database role used by the API has no access to the platform tables beyond what sign-in needs.
  • Automated cross-tenant tests: every endpoint called with another tenant's ids, sessions, links and file ids must return 404/401.
  • Per-tenant export and deletion (closing a workspace), and per-tenant audit logs.

8. Testing

  • Back end: tenancy unit tests (routing, caches, search_path), cross-tenant isolation suite, sign-up/verification/provisioning, each domain pack's rules, query-budget tests.
  • Front end: sign-up flow, workspace picker, domain-first navigation and terminology per domain.
  • End-to-end: sign up once per domain, verify e-mail, sign in, create the domain's core record and move it through its stages; isolation check between two firms; performance run with injected latency.

9. Neon and deployment

  • Neon main currently holds the single-tenant schema at revision 8ad0e7e5a8f8 with 7 users. After this work a SQL script (generated and verified the same way as before) upgrades it: platform schema plus the existing data as the first tenant.
  • New tenants are created by the application itself. The container used for development cannot reach Neon, so production provisioning runs from the deployed API.

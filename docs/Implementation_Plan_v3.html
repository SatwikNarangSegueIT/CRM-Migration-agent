2. Goals and scope

  • Configurable platform: administrators shape the CRM to their business without code: custom fields on any object, custom objects, picklists, apps, tabs, page sections, list views, reports, dashboards.
  • Complete standard apps: Sales (leads → conversion → accounts, contacts, opportunities with pipeline), Billing (products, price books, quotes, invoices, payments), Service (cases, queues, SLAs, customer portal), Marketing (campaigns, segments, email templates, bulk sends, consent, analytics), Analytics (reports, dashboards).
  • Industry packs: versioned bundles of objects, fields, apps, profiles, reports and server-side rules. First pack: Migration Agency (Australia).
  • Enterprise quality: fine-grained security, full audit and field history, tests, typed API, reproducible deployment.
  • Out of scope (v1): drag-and-drop page-layout designer, validation-rule and workflow builders, formula and roll-up fields, e-mail inbox sync, telephony, mobile apps, multi-currency, multi-tenant SaaS hosting (one deployment = one organisation). The engine leaves extension points for each.

3. Architecture: the metadata engine

Decision: every business object (standard or custom) is described by metadata and stored by one record engine. Platform tables (users, sessions, audit, profiles, metadata) stay normal relational tables.

ConcernDesign
Record storagerecords table: real columns for system fields (id, object_id, name, owner_id, record_number, created_at/by, updated_at/by, is_deleted, version, search_vector) plus a data JSONB column holding field values keyed by field API name.
RelationshipsLookup and master-detail values live in data and are mirrored in record_links (from_record, field_id, to_record) with real foreign keys, giving referential integrity, related lists and delete rules (restrict / clear / cascade).
ValidationEach write is validated against field definitions (type, required, unique, length, min/max, picklist membership, lookup target object and visibility) in the API before saving.
IndexesGIN index on data; fields marked filterable / unique / external id get a partial expression index ((data->>'field') WHERE object_id = …) created by the engine with CREATE INDEX CONCURRENTLY; uniqueness is enforced by a partial unique index.
Numbers & moneyJSONB numbers are exact decimals in PostgreSQL; the API uses Python Decimal. Currency fields store amounts in the organisation currency with 2 decimals.
Concurrencyversion integer; updates must send the version read (409 on mismatch).
Recycle binDeletes are soft (is_deleted) for 30 days, restorable, then purged by a job; hard delete for admins.
HistoryFields marked track history write old/new values to field_history; shown as a related list.
Business logicStandard objects and packs register Python object hooks (before/after create, update, delete; custom actions such as “Convert lead”). Hooks run inside the same transaction.
Why not one table per object?Runtime DDL for every custom field/object is slow, risky on a live database and complicates migrations. JSONB + expression indexes give the flexibility of Salesforce-style metadata with predictable operations. Limits: 200 custom objects, 400 fields per object, 25 indexed fields per object.

4. Customisation: objects, fields, relationships

Object definition

Label, plural label, API name (invoice, custom objects end in __c), icon and colour, description, name field (text or auto-number with format such as CASE-{00000}), record-number pattern, sharing default (section 9), feature switches: track history, allow activities, allow files, searchable, show in portal, allow reports. Standard objects cannot be deleted; their system fields cannot be removed.

Every field also has: help text, field-level security per profile (section 9), track history, filterable/sortable (creates an index), searchable (adds to full-text search), and section placement on the record page. Changing a field type is allowed only between compatible types (e.g. text → long text); otherwise the admin creates a new field. Deleting a field moves it to “deleted fields” for 15 days before data is purged.

Object Manager (Setup)

Create/edit objects and fields, reorder picklist values, arrange page sections (ordered list of sections and fields — not drag-and-drop canvas in v1), choose related lists, configure compact layout (fields in the highlights panel), and list default columns.

7. List views, record pages, search, import/export

List views (every object, including custom)

  • Header: object label, view name with view picker (“All Open Leads ▾”), pin as default, item count and summary line (“25 items • Sorted by Name • Filtered by Status • Updated a few seconds ago”).
  • Action bar: New, Import, Change Owner, Add to Campaign, Send Email, Delete (actions shown per object and permission); “Search this list…”; buttons for list settings, column chooser, refresh, sort, inline-edit mode, chart panel, filter panel.
  • Columns: any field the user can read (custom fields included), resizable, sortable on sortable fields, column header menus. Filters: field / operator / value with AND/OR logic, plus “My records / All records / My team / Queue”.
  • Saved views: private, shared with everyone, or with chosen roles/profiles; default view per user. Bulk selection, mass update, mass delete, change owner; inline edit respecting field-level security; keyset pagination; Kanban view for any object with a path picklist (opportunities by stage, cases by status).

Record pages

Highlights panel (icon, name, compact-layout fields, actions: Edit, Delete, Clone, Change Owner, Convert, Submit…), path with “Mark as current/complete” for path picklists, tabs: Details (sections from the page layout, inline edit), Related (related lists generated from relationships, each with New and View All), Activity timeline (log call, new task, new event, e-mail, note), History (tracked fields).

Search, import, export

  • Global search over searchable fields of every object the user can read (PostgreSQL full-text + trigram), grouped results, recent items.
  • CSV import wizard: choose object, upload, map columns to fields (auto-match by label), duplicate rule (match on e-mail / external ID → skip, update or create), dry-run preview, background job with error file.
  • Export of list views and reports to CSV (permission-controlled and audited).

8. Business logic of the standard apps

AreaRules
Lead conversionCreates or links Account and Contact, optionally an Opportunity; maps lead fields (including custom fields via an admin-defined mapping); copies activities and campaign memberships; marks lead converted (read-only afterwards). Duplicate check on e-mail and company name.
OpportunitiesStage drives probability and forecast category (editable mapping). Closed Won / Closed Lost are terminal; Closed Lost requires a reason. Amount = sum of opportunity products when products exist.
PricingEvery product has a standard price-book entry; custom price books override list price; quote and opportunity lines pick an active entry of one price book.
Quotes → InvoicesAccepted quote can generate an invoice (lines copied). Draft invoices are editable; issuing assigns the next invoice number and locks lines. Totals: line = qty × unit price − discount; tax per line from its tax rate (GST 10 % default for Australian organisations; tax-free lines allowed); rounding half-up to the cent.
PaymentsRecorded against issued invoices; status becomes partially paid / paid automatically; over-payment refused; void requires a reason and keeps history. Invoice and quote PDFs with tax-invoice fields (ABN, “Tax Invoice”).
CasesAuto-number; assignment to queue or user; SLA due dates from priority (configurable per priority); escalation flag when overdue (scheduled job + notification); status path New → Working → Waiting on Customer → Escalated → Closed; closing requires a resolution. Web-to-case form and customer portal create cases with origin set.
Customer portalContacts can be invited as portal users: view and create their own cases, comment, upload files, view their invoices. Portal profile is limited by design (section 10).
CampaignsMembers from leads/contacts or segments; member status values per campaign; campaign influence on opportunities (primary campaign source); actual cost, responses, won revenue roll up by report.
E-mail sendsRecipients = segment or campaign members, minus anyone without e-mail opt-in consent (or opted out), hard-bounced or duplicated. Every e-mail has an unsubscribe link and the sender's identity (Spam Act 2003 / GDPR-style). Sent in batches by workers; open pixel and click redirects tracked; unsubscribe updates consent immediately.
ActivitiesTasks and events attach to any activity-enabled object; reminders by notification and e-mail; calendar day/week/month views.

9. Security model: profiles, roles and sharing

Access is decided in four layers, all enforced on the server for every request, list, report, search and export.

LayerWhat it controls
1. Profile — system permissionsPlatform-wide abilities (table below). Each user has exactly one profile.
2. Profile — object permissionsPer object: Read, Create, Edit, Delete, VA View All (read every record regardless of sharing), MA Modify All (edit every record; delete every record only when D is also granted). Custom objects start with no access except for System Administrator.
3. Field-level securityPer profile and field: hidden, read-only or editable. Hidden fields are removed from API responses, list views, reports, search, exports and imports.
4. Record sharingOrganisation-wide default per object: Private · Public Read Only · Public Read/Write (detail objects inherit from master). Users always see records they own; the role hierarchy grants managers the access of their subordinates; sharing rules share records owned by a role/queue (or matching criteria) with another role or group (read or read/write); manual sharing on a record by its owner or an admin; queue members see queue-owned records.

Default org-wide sharing: Account, Contact: Public Read Only · Lead, Opportunity, Case, Quote, Invoice: Private · Campaign, Product, Price Book, Email Template: Public Read Only · Task/Event: Private (controlled by parent) · Custom objects: Private.

Default field-level security

  • All profiles: system fields read-only (created/updated by/at, record number, converted flags).
  • Opportunity Amount, Probability: read-only for Service Agent and Marketing. Account Annual Revenue: hidden for Service Agent and Portal.
  • Contact Birthdate: hidden for Marketing and Portal (other than own record). Payment Reference: visible only to Finance, Sales Manager, Read Only and System Administrator.
  • New custom fields: visible and editable to System Administrator only until the admin grants access (secure by default).

Default role hierarchy

CEO → Sales Director → Sales Manager → Sales Representative · CEO → Service Manager → Service Agent · CEO → Marketing Manager → Marketing User · CEO → Finance Manager → Finance Officer. Roles (who sees whose records) are separate from profiles (what a user can do); admins edit both.

Rules on top of the matrix

  • Records the user cannot see return 404; lookups only offer visible records; related lists, reports, search and exports apply the same filters.
  • Users cannot change their own profile or role, or deactivate themselves; the last active System Administrator cannot be removed.
  • Portal users never reach staff APIs; staff never use portal APIs.
  • Every permission, sharing and metadata change is audited.

12. Reports and dashboards

  • Report types: any reportable object, optionally with a related object (Accounts with Opportunities, Cases with Contacts, Campaigns with Members, custom objects). Custom fields included automatically.
  • Builder: pick columns, filters (with relative dates such as THIS QUARTER), grouping by up to 2 rows (summary) or rows × columns (matrix), aggregates (count, sum, average, min, max), sort, chart (bar, column, line, donut, funnel, KPI). Run-time security: users only see rows and fields they may see.
  • Folders: private, public, shared with roles/profiles. Dashboards: grid of report charts and KPIs with a “view as” running user and date filter; refresh on demand or scheduled.
  • Export & schedules: CSV export (Export Data permission, audited); scheduled e-mail delivery of reports (Celery beat).
  • Standard reports: pipeline by stage, forecast, win rate, lead conversion by source, campaign ROI, e-mail engagement, case volume/SLA compliance, aged receivables, revenue by month.

14. Platform security, compliance, performance

  • Phase 1 controls stay: hashed opaque sessions, CSRF token + Origin check, Argon2id, lockout, rate limits, TOTP MFA (mandatory for staff in production), append-only audit, security headers.
  • Query safety: the record engine builds SQL only from validated metadata (field API names whitelisted, values bound as parameters); user-supplied filters are parsed into an AST, never concatenated.
  • Data protection: encrypted field type for sensitive values (Fernet, key from secrets manager), S3 server-side encryption, private bucket and short-lived signed URLs, malware-scan hook for uploads.
  • Compliance: Privacy Act 1988 / APPs and GDPR-style features — consent records, data export per person, erasure (anonymise) workflow, retention policies per object, audit and field history.
  • Performance targets: list view p95 < 400 ms for 1 million records per object at 50 concurrent users (k6 load test); keyset pagination; expression indexes; report queries with statement timeout and row limits; heavy exports/imports in workers.

15. Testing, Neon, deployment

  • Tests: pytest unit + API tests for every engine rule (field validation for each type, sharing calculation, FLS stripping, list-view query builder, lead conversion, pricing and tax maths, invoice states, case SLAs, consent filtering); a generated test matrix checks each default profile × object × operation against section 10; Vitest component tests; Playwright end-to-end journeys per app; load and security (OWASP ZAP) scans.
  • Neon: unchanged from v2 — Sydney project, pooled endpoint for the app, direct endpoint for migrations, branch per pull request in CI. The Neon connector is connected to this workspace; no Neon project exists yet (to be created on approval).
  • Deployment: Docker images (API/worker/beat, nginx SPA), GitHub Actions CI/CD, staging → production with manual approval, AWS Sydney hosting recommended.

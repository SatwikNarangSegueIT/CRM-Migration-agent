1. Goals and scope

Build a production-grade CRM for an Australian migration agency, modelled on Salesforce concepts: Leads are converted into Contacts (clients), Organisations (accounts, e.g. employer sponsors) and Matters (visa cases, the equivalent of Opportunities/Cases). Every record has a Salesforce-style record page: highlights panel, stage Path, related lists and an activity timeline.

  • In scope: leads, contacts, organisations, matters, tasks & activities, documents, billing (service agreements, invoices, payments, client/trust account), client portal, reports with CSV export, administration, audit log, notifications.
  • Out of scope (v1): direct lodgement into ImmiAccount (no public API), e-mail inbox sync, SMS gateway, accounting-package sync (Xero/MYOB), mobile apps. The design leaves extension points for these.
  • Quality bar: role-based security enforced on the server, full audit trail, automated tests, typed API contract, reproducible deployments.

3. System architecture

  • Layered backend: routers (HTTP, validation) → services (business rules, permission checks, transactions, audit) → repositories/models (SQLAlchemy). Routers never touch the DB directly.
  • Single origin: SPA and API served under one domain (app.example.com and app.example.com/api) so session cookies stay first-party and SameSite=Lax works without CORS.
  • Stateless API processes: sessions in Postgres, jobs in Redis, files in S3 → horizontal scaling.

Key workflows and states

ObjectStates
Lead statusNEW → CONTACTED → QUALIFIED → CONSULTATION_BOOKED → CONVERTED; or UNQUALIFIED / LOST (reason required). CONVERTED only via conversion.
Matter stageCONSULTATION → AGREEMENT → DOCUMENT_COLLECTION → PREPARATION → READY_TO_LODGE → LODGED → FURTHER_INFO → DECISION. Status: OPEN / ON_HOLD / CLOSED. Outcome: GRANTED / REFUSED / WITHDRAWN / INVALID.
Matter rulesMoving past AGREEMENT requires a signed service agreement (admin can override with a reason, audited). Moving to LODGED, FURTHER_INFO or DECISION, and recording an outcome, requires matter.lodge. LODGED requires lodgement date and application reference. DECISION requires outcome and decision date.
Service agreementDRAFT → SENT → SIGNED, or CANCELLED. Signed agreements are immutable.
InvoiceDRAFT → ISSUED → PARTIALLY_PAID → PAID, or VOID (reason required). Only drafts are editable; numbers allocated on issue.
Checklist itemPENDING → RECEIVED → APPROVED, or REJECTED (needs replacement) / NOT_APPLICABLE.

Definition of "own"

  • Matters (case officer): user is the matter's case officer or responsible agent. Everything hanging off a matter (documents, checklist, messages, agreements, tasks on it) inherits this.
  • Matters (client): the client's contact is the primary client or a listed applicant on the matter.
  • Leads (intake): lead owner is the user, or the lead is unassigned (claiming sets the owner).
  • Tasks: user is assignee or creator; a task on an accessible matter is also visible.
  • Activities / global search: limited to records the user can read.

Additional access rules

  • Staff cannot use portal endpoints and clients cannot use staff endpoints (separate router groups with separate dependencies).
  • Only ADMIN may create or change another admin. Users cannot change their own role or deactivate themselves. The last active admin cannot be deactivated.
  • A record outside the user's scope returns 404 (not 403) so its existence is not disclosed.
  • Deletes are refused when dependent records exist (e.g. a contact with matters or invoices); most "deletes" are soft or replaced by deactivate/void.
  • Issued invoices and signed agreements are immutable; corrections are made by voiding / new versions.
  • Client-account withdrawals and transfers cannot exceed the client's balance (checked inside a locked transaction).
  • Implementation: one Python module holds the matrix (ROLE_PERMISSIONS); a FastAPI dependency require("matter.update") guards each route; scope helpers add WHERE clauses; a parametrised pytest suite tests every role × endpoint against this table.

9. API design

  • REST under /api/v1; OpenAPI at /api/docs (disabled in production or admin-only).
  • List endpoints: ?page=&page_size=&sort=&q= plus field filters; response { items, total, page, page_size }.
  • Errors: { "error": { "code", "message", "fields": {…} } }; 401 unauthenticated, 403 missing permission, 404 not found / out of scope, 409 state conflict, 422 validation.
  • Optimistic concurrency: updates send updated_at; mismatch → 409 so two staff cannot overwrite each other.
  • Idempotency keys on payment and trust endpoints.

10. Frontend design

  • Salesforce-style shell: top bar (app switcher, global search, notifications, user menu), object tabs (Home, Leads, Contacts, Organisations, Matters, Tasks, Billing, Reports, Admin) shown only when the user has the read permission.
  • List views: reusable DataTable with column sort, filters, search, pagination, saved views, bulk actions (assign owner, export).
  • Record pages: highlights panel, stage Path component with "Mark stage complete", details tab (inline edit), related lists, activity timeline with composer (log call / note / e-mail / task).
  • Matter board: Kanban by stage; drag-and-drop calls the same stage endpoint (server rules still apply).
  • Permission-aware UI: /auth/me returns the permission list; <Can permission="invoice.manage"> hides controls; route guards redirect; server remains the authority.
  • Client portal: separate, simplified layout under /portal, mobile-first.
  • Accessibility & UX: WCAG 2.1 AA, keyboard navigation, focus states, form error summaries, toasts, loading skeletons, empty states, responsive down to 360 px, Australian date (DD/MM/YYYY) and AUD formats.

12. Australian compliance support

The CRM supports compliance workflows; it does not by itself guarantee compliance. Requirements below should be confirmed by the principal against current OMARA guidance before go-live.
  • Code of Conduct for registered migration agents: service agreement record with scope, fees and estimated charges; flag that the Consumer Guide was provided; agreement gate before work progresses; client sign-off captured with name, time and IP.
  • Client money: separate client (trust) account ledger per client, no overdraw, transfer-to-office only against an issued invoice, full statement per client, reconciliation report.
  • Record keeping: documents, communications and billing retained; soft deletes; retention period configurable (default 7 years) with purge job requiring admin approval.
  • Registered-agent actions: lodgement and outcome recording restricted to matter.lodge; RMA MARA number stored on the user and shown on agreements and invoices.
  • Privacy Act 1988 / APPs: privacy and marketing consent fields, data minimisation, access logging, export of a client's data on request, data hosted in Australia (Neon Sydney, S3 Sydney).
  • GST: professional fees taxable at 10 % when the firm is GST-registered; government visa application charges passed through as GST-free lines; tax-invoice fields (ABN, "Tax Invoice" title) on PDFs.

13. Neon database operations

  • Region: create the Neon project in AWS Asia Pacific (Sydney) aws-ap-southeast-2. The region is fixed at project creation.
  • Two connection strings: DATABASE_URL = pooled endpoint (-pooler host, PgBouncer transaction mode) for the API and workers; DATABASE_URL_DIRECT = direct endpoint for Alembic migrations and long-running admin scripts.
  • Driver settings: psycopg 3 with sslmode=require. On the pooled endpoint use client-library (protocol-level) prepared statements only, never SQL PREPARE; if the deployed libpq is older than PostgreSQL 17, disable psycopg prepared statements (prepare_threshold=None) to stay safe. Avoid session-level features (LISTEN/NOTIFY, session advisory locks, SET without LOCAL) on pooled connections.
  • Pooling in the app: small SQLAlchemy pool (pool_size=5, pool_pre_ping=True, pool_recycle=300) because Neon can scale compute to zero and drop idle connections.
  • Branches: main (production), staging, and a short-lived branch per pull request created by CI for migration and E2E tests, deleted on merge.
  • Backups / restore: Neon point-in-time restore window sized for the plan; nightly logical dump (pg_dump) to S3 for long-term retention.
  • Cold starts: keep production compute always-on (disable scale-to-zero) to avoid first-request latency; allow scale-to-zero on dev branches.

15. Deployment and environments

  • Local: docker compose up runs API, worker, beat, Redis, MinIO (local S3) and the Vite dev server; database is a personal Neon dev branch (or local Postgres). scripts/seed.py creates one demo user per role.
  • Environments: development → staging → production, each with its own Neon branch/project, S3 bucket and secrets.
  • Containers: one Python image (API / worker / beat via command), one static frontend build served by CDN or Nginx.
  • Hosting (recommended): AWS Sydney (ECS Fargate or App Runner) to keep data in Australia, close to Neon aws-ap-southeast-2.
  • CI/CD (GitHub Actions): lint → test → build images → run alembic upgrade head on the direct endpoint → deploy → smoke test. Production deploys need manual approval.
